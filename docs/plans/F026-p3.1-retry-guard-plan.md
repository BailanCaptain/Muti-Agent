# F026 Phase 3.1 — 派发协议 retry 兜底层

**Feature:** F026 — `docs/features/F026-a2a-reliability-layer.md` (P3.1 · 2026-04-27 立项)
**Goal:** 在 P3 方案 X（`[Call: @人 任务]` 显式标签派发）落地后，用机制层兜底承接 LLM 写错协议的场景——派发预检 + agent retry + 实时可观测 + 失败硬警示——让用户**永远看不到 `[Call:]` 字面量**且**永远知道派发是否成功**。

**Acceptance Criteria（覆盖 spec M6）:**
- `detectInvalidDispatch` 单元 fixture 覆盖嵌套 `[Call:]`（R-054）+ 段首 `@X` 漏 `[Call:]` 包装（R-053）红 case
- assistant final 入库前预检命中 → 拒收 + retry（MAX 3 次）；3 次合规之一即入库；3 次都错则失败兜底
- `messages.retry_count` / `retry_reasons` migration 存在且写入正确
- `agent_events:dispatch_validation_retry` 实时广播 + 前端订阅渲染进度卡
- 前端历史 badge：`retry_count > 0` 气泡顶部贴提示
- 前端硬警示：失败兜底场景 @ pill 加红色斜杠 + 红色 banner
- `stripCallTags` 宽松版：嵌套输入用户视觉零 `[Call:]` 字面量
- 真机手验：R-053 / R-054 重跑全绿（前端 0 字面量泄露 + 派发失败有红条 + 进度卡可见）

**Architecture:**
- 派发预检：`mention-router.ts:detectInvalidDispatch(content) → { ok: boolean, reason?: "nested_call_tag" | "naked_at_with_real_teammate", details?: { ... } }`，纯函数，零副作用（2026-04-28 删 `naked_at_with_dispatch_intent` 模糊白名单；2026-04-29 R-057 重启「行首裸 @ 真名队友」分支兜底，详见 AC-2 / AC-19）
- Retry 触发：`message-service.ts` assistant final 入库前**首道闸门**——检测命中即不写 `messages` 表，发一个 internal event 给 runtime 让它续 prompt
- Retry 续 prompt：`claude-runtime.ts` 暴露 `resumeWithCorrection(threadId, reason)` API；走 `claude --resume <session> --append-system-prompt <retry hint>` 重新 stdin
- 可观测层：`agent_events` 新事件类型 `dispatch_validation_retry` + WS broadcast；frontend `chat-stream.tsx` 渲染实时进度卡
- 持久层：migration 加 `messages.retry_count INTEGER DEFAULT 0` + `retry_reasons TEXT DEFAULT '[]'`；frontend `markdown-message.tsx` 渲染历史 badge
- 前端解耦：`stripCallTags` 改宽松 regex（允许嵌套外层也脱掉）；与后端 `resolveCallTagMentions` 解耦（后端继续 fail-closed）

**Tech Stack:** TypeScript · node:test · zod · 复用 P3 方案 X regex / agent_events / WS broadcaster
**Phase Dependencies:** P3（方案 X 双契约 + B021 嵌套 fail-closed）必须已落
**Phase 下游影响:** P4 `0` 阻塞（不动 registry / DB CAS）；P5 提前实现「@ pill 状态：失败 + 失败重发按钮」AC 的失败分支

## Acceptance Criteria（Phase 3.1 · 客观可测）

### 后端 · `detectInvalidDispatch`

- [ ] **AC-1** 嵌套 `[Call:]` 检测：输入 `[Call: @A ... [Call: @B ...] ...]` → `ok=false, reason="nested_call_tag"`
- [x] **AC-2 历史决策记录**（2026-04-28 [A] 删模糊白名单 → 2026-04-29 R-057 重启精准兜底，**当前生效行为见 AC-19**）：原 [A] 决策走「含派发动词关键词」白名单太弱、误触发面过广（"@桂芬 也帮过我"、"@范德彪 写过 review" 这种装饰句被误判），故全删。**R-057 复盘**：彻底删 = 派发链静默断（仁勋写漏 [Call:] 时德彪不起来，用户体感是"喊了没反应"）。**修订后行为**（取代原 [A]）：裸 `@X` 命中**真名队友白名单**（`mention-router` 已知 agent 集合）即触发 retry；非真名（`@桂芬 也帮过我` 这种字串不在 roster）仍走装饰路径，不派发不 retry。回归断言：`@范德彪 review 这个 PR` → `ok=false, reason="naked_at_with_real_teammate"`（详见 AC-19）。
- [ ] **AC-3** 合法格式：输入 `[Call: @范德彪 review PR]` → `ok=true`
- [ ] **AC-4** 装饰性 `@`：输入 `我和 @桂芬 聊过` → `ok=true`（非段首 + 无派发意图）
- [ ] **AC-5** inline-code `[Call:]`：输入 `这里写 \`[Call: @X]\`` → `ok=true`（hard-negative 屏蔽与 P3 一致）
- [ ] **AC-6** Round-trip 与 `resolveCallTagMentions` 互补：合法 [Call:] 格式经 detect 通过 + resolveCallTagMentions 命中 = 双绿；嵌套格式 detect 拒绝 + resolveCallTagMentions 仅识别内层 = 双红（行为对齐）

### 后端 · retry 流程

- [ ] **AC-7** assistant final 入库前 hook：`message-service.ts` 在 `insertMessage(role=assistant, message_type=final)` 前调 `detectInvalidDispatch`；命中即拒收（不写 `messages` 表 / 不派发 / 不结束 invocation）
- [ ] **AC-8** Retry 触发：拒收时给 runtime 发 internal event；`claude-runtime.ts:resumeWithCorrection` 走 `claude --resume <native_session_id>` + 新 user message：`[系统] 上轮 final 派发格式不合契约：<reason>。请重写：合法格式 [Call: @人名 任务]，禁止嵌套，禁止段首 @ 但无 [Call:] 包装的派发意图。`
- [ ] **AC-9** Retry 上限 `MAX_DISPATCH_RETRIES=3`（env 可调）：第 1/2/3 次合规 → 入库且 `retry_count = 0/1/2`；3 次都错 → final 强制入库 + `retry_count=3` + `agent_events.dispatch_validation_retry` 末条 status=`exhausted`
- [ ] **AC-10** 集成测试 mock CLI：分别测「第 1 次合规」「第 1 次错+第 2 次合规」「3 次都错」三种路径；断言入库的 final 内容、`retry_count`、`retry_reasons` JSON

### 后端 · 持久 + 事件

- [ ] **AC-11** Migration `messages` 加 `retry_count INTEGER NOT NULL DEFAULT 0` + `retry_reasons TEXT NOT NULL DEFAULT '[]'`；零 downtime（新列 + DEFAULT 不阻塞老数据）
- [ ] **AC-12** `agent_events` 加事件类型 `dispatch_validation_retry`（payload zod schema：`{ threadId, attemptIndex, maxAttempts, reason, originalText, status: "retrying" | "settled" | "exhausted" }`）+ WS broadcast 通道（2026-04-29 同步：`settled` 字面量由 AC-21 引入，schema 真相源以 `packages/shared/src/realtime.ts` 为准）
- [ ] **AC-13** 事件 fixture：每次 retry 触发写入 1 条 `agent_event` 行 + WS push 1 条；事件按 `attemptIndex` 单调递增

### 前端 · UI

- [ ] **AC-14**（2026-04-29 撤回 ✅，手验失败）实时进度卡：订阅 `dispatch_validation_retry` event；渲染「🔄 派发格式不合契约，正在重写...（第 N 次 / 最多 3 次） · 原因：<reason>」；位置在该轮 assistant 消息气泡占位上方 — 原 2026-04-28 标完成，但手验暴露 **进度卡一直转圈不收尾** + **气泡 retry 期间从头流诡异感**。根因：`accept` / `retry-spawn-throw-exhaust` 两条路径 emit 缺失 + `message.created` 早于 retry 事件导致 page.tsx clearRetry 空操作。AC-14 的"进度卡可见"形式上达成，但收尾语义未达成 → 撤回，闭环到 AC-21/22 一并 Green。
- [ ] **AC-21**（2026-04-29 新增 · in-flight bug 归回 AC 内修）retry 进度卡收尾：accept 路径（合规入库）+ retry-throw-exhaust 路径（spawn 失败兜底）必须 emit `dispatch_validation_retry` 末条 event status=`"settled"` 或 `"exhausted"`，front store 收到 settled/exhausted 即清；不再依赖 `message.created` 间接清。shared zod schema 加 `"settled"` 字面量。
- [ ] **AC-22**（2026-04-29 新增 · UX 优化）retry 期间 streaming bubble 内容锁：retry 触发后到 settled/exhausted 前，气泡 streaming content 显式替换为「⏳ 正在按合规协议重写…（第 N/3 次）」占位文本，settled 后才以最终 content overwrite 显示——避免用户看到"从头流"的吞掉重写诡异感；exhausted 走 banner 红条接管。
- [ ] **AC-15** 历史 badge：`messages.retry_count > 0` 时气泡顶部贴「⚠️ 此回复自动重写 N 次（展开详情）」；展开看 `retry_reasons` 列表
- [ ] **AC-16** 失败硬警示：`retry_count >= MAX_DISPATCH_RETRIES` 时气泡顶部贴红色「❌ 派发协议反复写错（已重试 N 次）— 派发未触发，请手动 @ 触发」+ 该消息内所有 @ pill 加红色斜杠图标
- [ ] **AC-17** `stripCallTags` 宽松版：嵌套输入 `[Call: @A 描述里 [Call: @B] 接力]` 渲染输出**不含**外层 `[Call:` / 内层 `[Call:`字面量；保留 `@A 描述里 @B 接力` 文字 + 双 pill
- [ ] **AC-18** 与后端 `resolveCallTagMentions` 解耦：前端 strip 不再共享后端 regex（独立 fixture）
